Week 10 / Services

HTTP, TLS, and application boundaries

6 hours core+ 0–6 hours practicePrerequisite: Week 09

HTTP carries application messages over a connection. TLS encrypts transport and authenticates the server when certificate validation succeeds. Hashing detects changes; it does not hide information. A certificate being present is different from a client trusting the correct identity.

Power-on plan: UBU01 + UBU02 only, private switch. Preserve the port-80 site from Week 5.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

1. Read a request and response

UBU02 • Bash
curl -v http://10.77.0.11/
curl -I http://10.77.0.11/not-present

Identify method, path, Host header, response status, and content type. A 404 means the server answered but did not find the resource. A timeout means something different. Use only dummy headers and data in captures.

2. Issue a lab certificate

UBU01 • Bash
sudo mkdir -p /etc/nginx/lab-tls
sudo openssl req -x509 -newkey rsa:2048 -nodes -days 30 -keyout /etc/nginx/lab-tls/lab.key -out /etc/nginx/lab-tls/lab.crt -subj "/CN=10.77.0.11" -addext "subjectAltName=IP:10.77.0.11"
sudo chmod 600 /etc/nginx/lab-tls/lab.key

This self-signed certificate is for the lab only. The SAN records the IP identity being tested. The unencrypted private key is protected by filesystem permissions; never export it as portfolio evidence. Record its 30-day expiry.

3. Add HTTPS without removing HTTP

Use sudo nano /etc/nginx/sites-available/lab-tls and enter:

UBU01 • nginx site file
server {
    listen 443 ssl;
    server_name 10.77.0.11;
    ssl_certificate /etc/nginx/lab-tls/lab.crt;
    ssl_certificate_key /etc/nginx/lab-tls/lab.key;
    root /var/www/html;
    location / { try_files $uri $uri/ =404; }
}
UBU01 • Bash
sudo ln -s /etc/nginx/sites-available/lab-tls /etc/nginx/sites-enabled/lab-tls
sudo nginx -t
sudo systemctl reload nginx
sudo ufw allow from 10.77.0.0/24 to any port 443 proto tcp

Create the symlink once. If syntax validation fails, correct it before reload.

4. Validate trust explicitly

UBU02 • Bash
curl -I https://10.77.0.11
scp -i ~/.ssh/cyberlab_ed25519 learner@10.77.0.11:/etc/nginx/lab-tls/lab.crt ~/lab.crt
openssl x509 -in ~/lab.crt -noout -fingerprint -sha256 -dates
curl --cacert ~/lab.crt -I https://10.77.0.11

First request should fail certificate trust; final request should succeed. Compare the fingerprint with openssl output on UBU01’s console before trusting the file. Do not make -k or disabling certificate checks your permanent solution.

5. Compare visibility

Repeat Week 3’s tcpdump capture with tcp port 80 or tcp port 443. Generate one HTTP and one HTTPS request from UBU02. Read with tcpdump -A -r FILE. HTTP headers are visible; TLS application content should not be readable. Both still expose traffic metadata. Inspect nginx access.log to see the server-side request record.

Pass this week

  • Certificate fingerprint, SAN, expiry, and trust test
  • HTTP/TLS packet comparison
  • Service diagram showing encryption termination

Explain without the guide

  • What does TLS not protect after the server decrypts a request?
  • Why is a hash not encryption?

If something fails

Certificate expired: issue a new lab certificate, reload nginx, verify fingerprint again, and replace the client trust file. Permission denied reading key: inspect file path and nginx startup privileges; do not make private keys world-readable.

Optional practice · 0–6 extra hours

Sketch a threat model for a small appointment app: assets, users, trust boundaries, three threats, and matching controls.
