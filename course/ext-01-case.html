Security platform extensions / Module 1

E1 · Prepare a shared investigation and review network

Prerequisites: Core Weeks 1–14. No Elastic, Splunk, or Security Onion experience required.

Time: Three two-hour sessions: build, test, review. Extend the estimate if installation or a failed gate needs more time.

Power-on plan: Host only for case preparation; then one new Ubuntu guest at a time. Keep original course VMs off.

Different products should lead to defensible conclusions from the same evidence. CASE-M01 is deliberately synthetic: it combines a short sequence of failed logins, ordinary web requests, process records, and a file change. The packet capture contains only its four HTTP transactions. It cannot corroborate the login or Windows records.

1. Download and preserve the case

Download CASE-M01 to C:\CyberLab\Evidence. In File Explorer right-click → Extract All. Confirm the extracted case-m01 folder contains events.ndjson, events.bulk.ndjson, auth-input.ndjson, auth-bad.ndjson, http-access.log, web-case.pcap, README.txt, SHA256SUMS, and mentor-answer-key.json. Read README first; leave the answer key closed until you have attempted the questions.

HOST • PowerShell; adjust only if extraction created an extra folder
Get-FileHash C:\CyberLab\Evidence\case-m01\events.ndjson -Algorithm SHA256
Get-FileHash C:\CyberLab\Evidence\case-m01\web-case.pcap -Algorithm SHA256

Compare with SHA256SUMS. A matching hash proves unchanged bytes relative to this supplied manifest, not independent provenance. Preserve the original ZIP and do exercises on copies. Do not change timestamps to make old events appear in a “last 15 minutes” search.

2. Inspect the format before importing

HOST • PowerShell
$caseRows = Get-Content C:\CyberLab\Evidence\case-m01\events.ndjson | ForEach-Object { $_ | ConvertFrom-Json }
$caseRows.Count
$caseRows | Group-Object { $_.event.dataset } | Select-Object Name,Count
$caseRows | Select-Object -First 1 | ConvertTo-Json -Depth 8

NDJSON means one complete JSON object per line. There are 16 normalized events across four sources. event.id identifies an event; labels.case_id ties the story together. @timestamp is event time in UTC. These fields are inspired by common security schemas, but this is not a full ECS or Splunk CIM dataset and it is not native Sysmon or Wazuh output.

3. Write hypotheses and negative tests

Before opening any SIEM, answer: Which user had repeated failures? Was there a later success? Did /private.txt return content? Was the Windows command destructive? Write “unknown” where evidence is insufficient. Define four queries: failed logins by user/source; all HTTP statuses; the CYBERLAB-M01 command marker; and a non-existent user that must return zero. Record the fixed search interval: 2026-09-01 09:59:00 through 10:03:00 UTC.

4. Build a separate host-accessible review network

The original CyberLab-Private network remains for live exercises. This new Internal switch connects the host to review guests for SSH and file transfer; it is not equivalent to the private isolation boundary. In administrator PowerShell inspect existing interfaces and routes. If 10.78.0.0/24 overlaps a real network or VPN, stop and agree a different unused subnet with the mentor, then consistently replace it in these extension instructions.

HOST • administrator PowerShell; run the final two lines only if not already configured
Get-VMSwitch | Format-Table Name,SwitchType
Get-NetIPAddress -AddressFamily IPv4 | Format-Table InterfaceAlias,IPAddress,PrefixLength
Get-NetRoute -AddressFamily IPv4 | Format-Table DestinationPrefix,InterfaceAlias
New-VMSwitch -Name CyberLab-Review -SwitchType Internal
New-NetIPAddress -InterfaceAlias "vEthernet (CyberLab-Review)" -IPAddress 10.78.0.1 -PrefixLength 24

Do not configure NAT, Internet Connection Sharing, a bridge, or a default gateway on this adapter. Keep Windows Firewall on. No inbound host service is required. This network is only for reviewing dummy data with patched tools; never move the Week 18 simulator or a vulnerable target here.

5. Understand the new VM profiles

Create ELASTIC01 in E2 (8 GB RAM, 4 vCPU, 80 GB disk) and SPLUNK01 in E4 (6 GB, 2 vCPU, 60 GB disk). Both use Ubuntu Server 24.04, installed using the existing Week 2 wizard. Download packages on Default Switch, then move the sole adapter to CyberLab-Review with static .40 or .41/24, no gateway, and no DNS. Install openssh-server, curl, nano, jq, unzip, and ca-certificates while online. Allow guest TCP 22 only from 10.78.0.1 before enabling ufw. Use console access for recovery. Browser interfaces will bind to guest loopback and travel through SSH tunnels.

Security Onion uses its own 8 GB/4-vCPU/200 GB appliance and an explicitly documented Default Switch management exception in E5. Never run two SIEM appliances together on 16 GB. These are tiny training allocations, not vendor production reference sizing.

6. Prepare the file-transfer workflow

When a review guest is ready, verify its SSH host-key fingerprint in the guest console using sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub. Compare it at first connection. From the host, use scp -r C:\CyberLab\Evidence\case-m01 learner@10.78.0.40:~/ for Elastic, or substitute .41 for Splunk. A guest password is acceptable for initial isolated transfer; it must be unique. If adopting SSH keys, repeat Week 6’s key test before disabling password login. In the guest run cd ~/case-m01 followed by sha256sum -c SHA256SUMS. Every file must pass.

Pass this module

  • Original hash comparison and working-copy manifest
  • Written hypotheses and four planned queries
  • Internal-switch configuration and a power-on plan

Explain without the guide

  • Why does this PCAP not prove the SSH login sequence?
  • How does an Internal switch differ from the original Private switch?

If something fails

Wrong extraction path: find README.txt before changing commands. Host cannot SSH: verify guest static IP, sole adapter, ssh service, and guest rule permitting .1. Do not enable a host inbound firewall rule to fix a guest SSH problem.
