Week 04 / Foundations

Linux files, users, and least privilege

6 hours core+ 0–6 hours practicePrerequisite: Week 03

Linux permissions distinguish owner, group, and everyone else. Read, write, and execute mean different things on files and directories. Least privilege means giving a task only the access it needs. A service account, a human user, and root serve different purposes.

Power-on plan: UBU01 + UBU02 on CyberLab-Private. Wazuh and Windows VMs do not exist yet.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

1. Navigate without guessing

Ubuntu guest • Bash
pwd
ls -la
mkdir -p ~/lab/week04
cd ~/lab/week04
printf "security notes\n" > notes.txt
cat notes.txt
cp notes.txt notes-backup.txt
ls -l

The tilde means your home directory; > replaces file contents, while >> appends.

  1. Before using either, read the destination carefully.
  2. Never practice destructive commands against /, /etc, or personal files.

2. Create a controlled access boundary

Ubuntu guest • Bash
sudo addgroup labreaders
sudo adduser analyst
sudo usermod -aG labreaders analyst
sudo mkdir -p /srv/labshare
sudo chown root:labreaders /srv/labshare
sudo chmod 750 /srv/labshare
printf "dummy case data\n" | sudo tee /srv/labshare/case.txt
sudo chown root:labreaders /srv/labshare/case.txt
sudo chmod 640 /srv/labshare/case.txt

Use a unique lab password for analyst.

The group may read the file but not change it; other users cannot enter the directory. tee writes standard input to a file with the specified privilege.

3. Test allowed and denied operations

Ubuntu guest • Bash
sudo -u analyst cat /srv/labshare/case.txt
sudo -u analyst sh -c "echo changed >> /srv/labshare/case.txt"
sudo -u nobody cat /srv/labshare/case.txt
namei -l /srv/labshare/case.txt

Check: Expect the first read to succeed, the write to fail, and nobody’s read to fail.

Save all three results.

A security control is unproven until both its allowed and denied cases are tested.

4. Inspect process identity

Ubuntu guest • Bash
ps -eo user,pid,ppid,comm --sort=user | head -30
systemctl status nginx --no-pager
sudo ss -lntp
id learner
sudo -l
  1. Find nginx’s worker user and listening socket.
  2. Explain why a process may need a privileged startup operation but perform routine work under a limited identity.
  3. Do not add analyst to sudo.

5. Break and repair one permission

Ubuntu guest • Bash
sudo chmod 600 /srv/labshare/case.txt
sudo -u analyst cat /srv/labshare/case.txt
sudo chmod 640 /srv/labshare/case.txt
sudo -u analyst cat /srv/labshare/case.txt
  1. Write a change record with the symptom, reason, correction, and verification.
  2. Keep the sample directory for later file-integrity exercises.
  3. Do not “fix” access by using chmod 777.

Pass this week

  • Permission matrix with successful and denied tests
  • Process/user/socket map
  • Repair record

Explain without the guide

  • Why can readable files still be inaccessible through a directory?
  • How is sudo different from being a member of labreaders?

If something fails

A newly added group may not appear in an existing interactive session; sign out/in. sudo -u starts a fresh identity for these checks. Inspect every parent directory with namei before widening permissions.

Optional practice · 0–6 extra hours

Use setfacl/getfacl after installing acl in update mode; compare an explicit user ACL with group permissions.
