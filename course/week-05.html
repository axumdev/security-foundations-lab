Week 05 / Systems

Services, logs, and recoverable configuration

6 hours core+ 0–6 hours practicePrerequisite: Week 04

A service manager starts and supervises long-running programs. Configuration describes intended behavior; sockets and requests reveal actual behavior. Logs are records of events, not complete truth. Accurate time and a known collection path make those records useful.

Power-on plan: UBU01 + UBU02 on private switch.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

1. Make the web service observable

UBU01 • Bash
sudo systemctl enable --now nginx
sudo nginx -t
curl -I http://127.0.0.1
sudo ss -lntp
sudo journalctl -u nginx --since "15 minutes ago" --no-pager
UBU02 • Bash
curl -I http://10.77.0.11

127.0.0.1 is loopback: the current machine. A local request succeeding does not prove a remote request will work. Record HTTP status, process, and port.

2. Produce a harmless log event

Ubuntu guest • Bash
logger -t cyberlab "week05 baseline event"
sudo journalctl -t cyberlab --since "5 minutes ago" --no-pager
date -u
timedatectl

Record UTC timestamps in evidence. In private mode time synchronization through the internet is unavailable; compare guest clocks with the host and correct large differences through a controlled update session. Explain local display time versus UTC.

3. Change nginx deliberately

Back up the site file, then open it. Inside its existing server block add the header below; do not replace the entire configuration.

Ubuntu guest • Bash
sudo cp /etc/nginx/sites-available/default /etc/nginx/sites-available/default.w05-backup
sudo nano /etc/nginx/sites-available/default
UBU01 • add inside nginx server block
add_header X-Lab-Owner "learner" always;
Ubuntu guest • Bash
sudo nginx -t
sudo systemctl reload nginx
curl -I http://127.0.0.1

Only reload if the syntax check succeeds. Expect the X-Lab-Owner header. Note that a reload can preserve service availability while adopting valid configuration.

4. Diagnose a controlled outage

UBU01 • Bash
sudo systemctl stop nginx

From UBU02 repeat curl -I http://10.77.0.11. Observe failure. Work in order: IP reachability, listening socket, process/service state, configuration check, service log. Then restore:

UBU01 • Bash
sudo nginx -t
sudo systemctl start nginx
curl -I http://127.0.0.1

Repeat the remote request too. Do not label a service incident “fixed” solely because its process started.

5. Preserve evidence

Ubuntu guest • Bash
mkdir -p ~/lab/week05
sudo journalctl -u nginx --since today --no-pager > ~/lab/week05/nginx-journal.txt
sudo tail -30 /var/log/nginx/access.log > ~/lab/week05/access-tail.txt
sha256sum ~/lab/week05/*.txt

Write what the access log can establish (requests recorded by nginx) and what it cannot establish (the real person behind an address or requests never reaching nginx).

Pass this week

  • Change and rollback plan
  • Before/after header output
  • Outage timeline with remote recovery proof

Explain without the guide

  • What can be listening when the application is still broken?
  • Why do we validate syntax before reload?

If something fails

nginx -t fails: restore the backup or correct the reported line before restarting. Empty journal is not always missing traffic: nginx access requests normally go to its access.log.

Optional practice · 0–6 extra hours

Create a tiny systemd service that runs python3 -m http.server 8080 as learner, then inspect its journal. Keep it private and remove the practice unit afterward.
