Week 12 / Detection

Collect Linux events and prove file monitoring

6 hours core+ 0–6 hours practicePrerequisite: Week 11

Collection brings events to the manager; detection turns selected events into alerts. File integrity monitoring (FIM) notices changes relative to a baseline. An alert is a lead for investigation, not automatic proof of malicious activity.

Power-on plan: WAZUH01 8 GB + UBU01 2 GB. Private switch for tests. Use the temporary management path only to inspect results afterward.

For dashboard access and file transfers, use the complete temporary management procedure in the lab handbook, including the explicit host key path and cleanup checks.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

1. Install a matching Linux agent

In UBU01 update mode, download the Linux amd64 DEB matching your recorded Wazuh manager release from the official packages list. For the checked release the filename is wazuh-agent_4.14.7-1_amd64.deb. If the manager differs, select the matching package instead. Compare the published SHA512 hash using sha512sum. Bring UBU01 back to private mode before starting enrollment.

UBU01 • Bash; run from the download directory
sudo env WAZUH_MANAGER="10.77.0.30" WAZUH_AGENT_NAME="UBU01" dpkg -i ./wazuh-agent_4.14.7-1_amd64.deb
sudo systemctl daemon-reload
sudo systemctl enable --now wazuh-agent
sudo tail -40 /var/ossec/logs/ossec.log

If installation reports missing dependencies, resolve them in update mode using apt, then return private. Expect a successful manager connection. The enrollment port is TCP 1515 and event traffic uses TCP 1514 in this course.

2. Verify at both ends

WAZUH01 • Bash
sudo /var/ossec/bin/agent_control -l

Find UBU01 as active. In the dashboard select Agents management → Summary and open UBU01. Record last keepalive and version. If dashboard labels change, look for the agent inventory rather than assuming collection failed.

3. Configure a tiny FIM scope

On UBU01 back up /var/ossec/etc/ossec.conf. Open with sudo nano. Inside the existing syscheck block add the directory entry below; do not create a second syscheck block or overwrite the whole file.

UBU01 • inside existing <syscheck>
<directories realtime="yes" check_all="yes">/srv/labshare</directories>
UBU01 • Bash
sudo systemctl restart wazuh-agent
sudo tail -30 /var/ossec/logs/ossec.log

Wait for the initial scan to finish before changing a file. If service startup reports an XML error, restore the backup and correct the tag placement.

4. Generate and correlate one change

UBU01 • Bash
date -u
printf "week12 approved change\n" | sudo tee -a /srv/labshare/case.txt
sudo sha256sum /srv/labshare/case.txt

Wait up to a few minutes. In Wazuh’s file integrity view, filter agent UBU01 and the exact file path; expand the time range if needed. Identify action, timestamp, and changed attributes. On the manager inspect sudo tail -50 /var/ossec/logs/alerts/alerts.json. An unchanged rewrite may not produce the same alert as a content change.

5. Prove the collection boundary

Create ~/unmonitored-lab.txt outside the configured directory and change its contents. Your custom directory monitoring should not claim coverage there. Check other default FIM paths before concluding it is unmonitored. Then stop the UBU01 agent for two minutes, change the monitored file once, restart it, and record whether a later scan reports the difference. Do not assume realtime collection reconstructs every missed intermediate edit.

6. Write a detection test record

Document event generation time, source file, agent status, manager alert, dashboard evidence, latency, and collection gaps. Remove test-only data if necessary after saving evidence. Keep the FIM scope small to avoid flooding or exposing real documents.

Pass this week

  • Active agent at endpoint and manager
  • FIM change with source-to-dashboard trace
  • Negative test and stopped-agent coverage limitation

Explain without the guide

  • What is the baseline?
  • Why can a file alert be expected administrative activity?

If something fails

No alert: check agent connection, exact monitored path, baseline completion, changed content, manager alerts.json, and dashboard time filter in that order. Do not reinstall the stack as the first diagnostic step.

Optional practice · 0–6 extra hours

Configure one additional dummy directory and compare content, owner, and permission change alerts.
