Security platform extensions / Module 5

E5 · Investigate packet evidence in Security Onion

Prerequisites: E1, core Week 16, and saved results from E2–E4.

Time: Three two-hour sessions: build, test, review. Extend the estimate if installation or a failed gate needs more time.

Power-on plan: SOIMPORT only: 8 GB RAM, 4 vCPU, 200 GB dynamically expanding disk, one management NIC. Other guests off. No live sniffing NIC.

Security Onion combines network evidence, detections, and investigation tools. On this laptop you will use IMPORT mode for offline packet evidence. This is not a full live network deployment, and the normalized JSON fixture is not a Windows EVTX file.

1. Check capacity and get the appliance ISO

Download the official Security Onion 2.4 ISO from its Download page and compare the published checksum with Get-FileHash on the host. Record the exact release. Use the official ISO, not an Ubuntu network installation. Check host storage in File Explorer → This PC. Keep at least 50 GB free for Windows and growth after the planned lab usage; a dynamically expanding 200 GB disk can still fill the real SSD. Pause if the combined VM/ISO/checkpoint plan would exceed available storage.

The hardware page lists a smaller Import disk minimum, while the first-time tutorial specifies 200 GB. This course follows the conservative 200 GB allocation, with 8 GB guest RAM. Evaluation and Standalone are different modes; Standalone’s 24 GB minimum guest RAM does not fit this 16 GB host. A full sensor deployment belongs on a mentor server/cloud environment with separately checked sizing.

2. Create the VM with one management adapter

Hyper-V Manager → New → Virtual Machine: SOIMPORT; Generation 2; startup memory 8192 MB; leave Dynamic Memory disabled; Default Switch; create a 200 GB VHDX; attach the verified Security Onion ISO. Before starting, Settings → Processor → 4 virtual processors, and Security → disable Secure Boot for this guest only if the ISO cannot boot with the selected template. Do not disable host Secure Boot. This is a Hyper-V adaptation of the vendor ISO workflow, not a claim of a vendor-tested Hyper-V configuration.

This guest has a documented management exception: Default Switch provides update/setup connectivity and host browser access. It is not on the isolated live-exercise network. Use only the supplied benign packet file, never live attacks or unknown malicious captures. Do not bridge an adapter, forward router ports, or add a sniffing NIC.

3. Install the operating system and choose IMPORT

Start the VM and use the ISO’s installation option. The installer erases the selected virtual disk: verify this is the new SOIMPORT disk. Set the local account/password when prompted and complete installation. Eject the ISO when installation finishes and reboot to the installed disk. Sign in at the VM console; follow the Security Onion Setup prompts.

Select the IMPORT deployment role. Use Standard connectivity for this online setup, hostname soimport, and the single management interface. Select DHCP for the Hyper-V Default Switch; record the assigned IPv4 address, gateway, and DNS. Do not copy an address from the 10.78 review network. Accept a Docker subnet only after verifying it does not overlap the host/VPN networks. Use direct internet access unless your actual connection requires a proxy.

4. Create console access and finish setup

Create the Security Onion Console web account with a unique password (separate from the local operating-system account). For web access choose the management IP when the wizard offers IP versus hostname. Allow analyst access only from the host’s Default Switch IPv4 address: find it in host PowerShell with Get-NetIPAddress -InterfaceAlias "vEthernet (Default Switch)" -AddressFamily IPv4. Do not allow 0.0.0.0/0 or the whole household subnet. Review the setup summary for IMPORT and one management interface before confirming.

Wait for setup completion; first boot can be slow. In the guest use sudo so-status to inspect services. Browse https:// followed by the recorded guest management IP from the host. For the initial self-signed certificate, confirm the address belongs to this guest and record the certificate fingerprint from the browser; do not carry a global certificate-validation bypass into other labs. Sign in and open Grid; wait for the expected Import services to become healthy. Some screens and labels vary by 2.4 patch; record differences with the mentor.

5. Import the PCAP once

In Grid locate the Import node and its upload/import action. Select the host working copy of web-case.pcap and submit. Wait for processing to finish before searching. Preserve the original hash and import status. The supported CLI alternative is sudo so-import-pcap /full/path/to/web-case.pcap after an authorized file transfer, but choose one route, not both. Import retains packet timestamps, so “last 15 minutes” will not find this case.

Open Hunt and set the absolute case time range, September 1, 2026, 09:59–10:03 UTC (convert if the UI displays local time). Start with a broad search, expand a record, and use the field action/menu to filter the original client IP 10.77.0.12. Inspect the dataset field and select the Zeek HTTP dataset using the UI filter. Field names vary with parser versions; copy the resulting query into your notebook rather than assuming the normalized JSON field names were imported.

6. Reconstruct four HTTP transactions

Find the four request paths /, /private.txt, /does-not-exist, and /status. Add time, client/server IP, request URI, and response status to the result columns using the field menu. Expect four HTTP transactions with statuses 200, 404, 404, 200. The complete PCAP has 32 packets; packet count is not HTTP transaction count. Open the related session/PCAP view where available and inspect a request and its empty response.

Use the same query builder to search for /never-requested and require zero HTTP records. Then inspect Alerts for the case interval. Zero IDS alerts is a valid result for this benign capture; it does not mean ingestion failed. Use the HTTP records and import status as ingestion proof. If an informational signature fires, record its rule and explain it without asserting a compromise. This PCAP contains no SSH or Windows process records, so mark those questions “not observable in this source.”

7. Diagnose access and preserve a report

If browser access fails, confirm the guest IP in the console and the current host Default Switch IP; Hyper-V may change this subnet. Verify so-status before editing firewall rules. Security Onion manages its firewall; do not make direct iptables changes. To add the actual current host IP, use sudo so-firewall includehost analyst HOST_IP, replacing HOST_IP with the observed address only. Remove stale allow entries through Administration → Configuration → firewall host groups after access returns. Never widen to all addresses as a shortcut.

Export the query text, four transaction rows, zero-result test, packet/session observation, and alert interpretation. A repeated identical PCAP may be deduplicated; do not delete backend directories to force another import. Preserve the successful first import and repeat the queries instead. Sign out and shut down the guest with sudo poweroff.

Pass this module

  • IMPORT role, one management interface, restricted host access, and healthy services
  • Four HTTP transactions and their status codes, with original timestamps
  • Zero-result test and an explicit account of what the PCAP cannot prove

Explain without the guide

  • Why can zero alerts coexist with successful network evidence ingestion?
  • Why is an IMPORT appliance not a continuous network monitoring deployment?

If something fails

No results: inspect upload completion, absolute UTC range, and broad records before applying dataset filters. Resource pressure: keep every other VM off and inspect host RAM/storage; extend the exercise on mentor hardware rather than allocating more RAM than the laptop owns. Unsupported ISO/Hyper-V issue: stop and record the boot error for mentor review.
