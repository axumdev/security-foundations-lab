Week 20 / Assurance

Containers and data exposure

6 hours core+ 0–6 hours practicePrerequisite: Week 19

A container shares its host kernel. An image supplies software; a container is an instance. Port publication and filesystem mounts cross boundaries. A read-only mount prevents writes through that mount but does not prevent accidental disclosure of the mounted files.

Power-on plan: UBU01 + UBU02 only, private switch during all container runs. Docker runs inside UBU01, never on the Windows host.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

Expanded track: See the six security-platform labs and schedule for Elastic, Splunk, and Security Onion. Budget these hours separately from the core; complete their comparison report for the final review.

1. Install the Ubuntu-packaged engine

In UBU01 update mode, stop nginx, install docker.io, and pull the training image. This course uses Ubuntu’s packaged Docker engine; do not mix it with Docker’s separate repository packages. Do not add learner to the docker group, which would grant broad host control.

UBU01 • Bash, update mode
sudo apt install docker.io
sudo systemctl enable --now docker
sudo docker pull nginx:stable-alpine
sudo docker image inspect nginx:stable-alpine --format '{{index .RepoDigests 0}}'

Record the returned digest. The tag can change over time. Return to private mode before running containers. Docker’s published ports can bypass expected ufw filtering; isolation and explicit bind addresses are essential.

2. Prepare a deliberate dummy exposure

UBU01 • Bash
mkdir -p ~/lab/week20/published ~/lab/week20/private
printf "Public training page\n" > ~/lab/week20/published/index.html
printf "DUMMY-ONLY-INTERNAL-NOTE\n" > ~/lab/week20/published/internal.txt
sudo docker run -d --name labweb -p 10.77.0.11:8080:80 --mount type=bind,src="$HOME/lab/week20/published",dst=/usr/share/nginx/html,readonly nginx:stable-alpine

The bind exposes TCP 8080 only at the private guest address. The mount is read-only but deliberately includes a file that should not be served. It contains no actual secret.

3. Test the boundary from the client

UBU02 • Bash
curl -i http://10.77.0.11:8080/
curl -i http://10.77.0.11:8080/internal.txt

Both requests should succeed before remediation. On UBU01 inspect sudo docker ps, sudo docker logs labweb, and sudo docker inspect labweb. Find the port binding and mount source.

4. Remediate and retest

UBU01 • Bash
mv ~/lab/week20/published/internal.txt ~/lab/week20/private/internal.txt

Repeat both HTTP requests. Public index should remain available; internal.txt should now return 404. Explain why the readonly flag alone did not solve disclosure. Preserve only the dummy example in your portfolio.

5. Remove the workload and verify

UBU01 • Bash
sudo docker stop labweb
sudo docker rm labweb
sudo docker ps -a

From UBU02 repeat the request with --max-time 5; it should fail. Keep the image cached if repeating the lab. Ensure no container runs before reconnecting UBU01 for internet updates or dashboard management. Do not mount /, /var/run/docker.sock, or real credentials into a training container.

6. Write a short threat model

List assets, trusted users, image supplier, published port, host mount, and two threats: unintended files served and excessive container privilege. Describe controls and how you would test them. Compare container isolation with a VM; neither is a reason to skip patching.

Pass this week

  • Image digest and container boundary diagram
  • Public success/private-file denial after correction
  • Container cleanup and threat model

Explain without the guide

  • Why did a read-only mount still disclose data?
  • How can port publication surprise firewall assumptions?

If something fails

Container name in use: inspect docker ps -a and remove only the prior stopped labweb. Port conflict: inspect the exact 8080 listener. Mount empty: verify the absolute source path and file permissions.

Optional practice · 0–6 extra hours

Inspect image layers and the configured user. Research the official image’s documented support for read-only root filesystems before attempting additional hardening.
