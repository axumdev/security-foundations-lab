Week 06 / Systems

SSH keys, firewalls, and a foundation exam

6 hours core+ 0–6 hours practicePrerequisite: Week 05

Authentication proves an identity; authorization decides what that identity may do. A firewall filters connections, not user intentions. SSH keys let the server verify possession of a private key without sending that key across the network.

Power-on plan: UBU01 server + UBU02 client on private switch. Keep the UBU01 console open while changing SSH or firewall rules.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

1. Create a client key

UBU02 • Bash
ssh-keygen -t ed25519 -f ~/.ssh/cyberlab_ed25519
ssh-copy-id -i ~/.ssh/cyberlab_ed25519.pub learner@10.77.0.11

Set a passphrase when prompted. Accept a host key only after comparing it with sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub in UBU01’s console. The public key may be copied; the private file remains on UBU02. ssh-copy-id needs the learner password once.

2. Prove key login before hardening

UBU02 • Bash
ssh -i ~/.ssh/cyberlab_ed25519 -o PasswordAuthentication=no learner@10.77.0.11

Run hostname and whoami in the new session, then exit. If this fails, fix key ownership and connectivity before proceeding.

3. Configure the server safely

On UBU01 create /etc/ssh/sshd_config.d/00-cyberlab.conf with the three lines below. A leading 00 makes this early in the include order; still verify effective settings because other configuration can affect them.

UBU01 • SSH configuration file
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
UBU01 • Bash
sudo sshd -t
sudo sshd -T | grep -E "passwordauthentication|kbdinteractiveauthentication|permitrootlogin"
sudo systemctl reload ssh

Use sudo nano to create the file as practiced in Week 3. Do not reload if validation fails. Open another key-authenticated session before closing the working console. Force a password-only attempt from UBU02 with ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password learner@10.77.0.11; expect denial.

4. Add a minimal firewall policy

UBU01 • Bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 10.77.0.12 to any port 22 proto tcp
sudo ufw allow from 10.77.0.0/24 to any port 80 proto tcp
sudo ufw enable
sudo ufw status numbered

From UBU02 verify SSH and HTTP still work. Then temporarily delete the numbered HTTP allow rule using sudo ufw delete NUMBER, where NUMBER is the current HTTP rule’s displayed index. Re-test HTTP with curl --max-time 5 -I http://10.77.0.11; expect failure. Re-add the HTTP rule and prove recovery. Rule numbers change after deletion; inspect them each time.

5. Sit the foundation exam

Without following earlier command blocks, explain the path of an HTTP request from UBU02 to nginx. Create a new read-only file for labreaders, prove another user is denied, stop/start a service, and locate the associated logs. Your mentor chooses one fault: wrong switch, stopped nginx, or wrong file permission. You get 45 minutes to diagnose, repair, and explain the evidence.

Pass this week

  • Key success and password denial evidence
  • Firewall allow/deny/recovery results
  • Foundation exam scored with the rubric

Explain without the guide

  • Why keep the VM console available during hardening?
  • What protection does a private-key passphrase provide?

If something fails

SSH lockout: use UBU01’s Hyper-V console. Check ufw status, sshd -t, effective sshd settings, and journalctl -u ssh. Restore only the changed file/rule. Do not globally disable every control as a first response.

Optional practice · 0–6 extra hours

For 9–12-hour weeks, rebuild UBU02 from the ISO and recover the notebook. Keep the private key out of public evidence.
