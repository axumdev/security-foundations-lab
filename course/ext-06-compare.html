Security platform extensions / Module 6

E6 · Defend an engineering decision across platforms

Prerequisites: Core Weeks 14–16 and E1–E5. Use saved evidence; resume only one appliance at a time.

Time: Three two-hour sessions: build, test, review. Extend the estimate if installation or a failed gate needs more time.

Power-on plan: Host for the report; ELASTIC01 alone for the access-control test. No simultaneous SIEM stack.

A security professional explains coverage, blind spots, cost, failure modes, and operational ownership. Your final deliverable is a defensible decision for a small organization, supported by experiments rather than product preference.

1. Build the evidence comparison

Create a table with one column each for Wazuh core labs, Elastic CASE-M01, Splunk CASE-M01, and Security Onion PCAP.

Rows: source/format; live versus file ingestion; timestamps; event count; failed logins; HTTP outcomes; process evidence; positive detection; negative test; role control; retention; backup; resource use; license and expiry.

Use “not tested” or “not observable” where appropriate.

Wazuh used separate live/replayed core exercises; do not claim it ingested the shared 16-event case.

Reconcile Elastic and Splunk: 16 canonical events, six failures, two successes, four HTTP events with two 404s, and one command marker. Security Onion supports only the four HTTP transactions. Differences caused by replay indexes, duplicates, time zones, or filters must be explained before comparing products.

2. Demonstrate least privilege in Elastic

Resume ELASTIC01, start es01/kib01, and open the E2 tunnel.

  1. As the administrator, Kibana → Stack Management → Security → Roles → Create role: lab_case_reader.
  2. Leave cluster privileges empty.
  3. Add index lab-case-m01 with read and view_index_metadata only.
  4. In Kibana privileges grant the current space Discover: Read (and Dashboard: Read only if needed); do not grant All.
  5. Save.
  6. Create a new local user case_reader with only this role and a unique password through Users.
  7. Sign out and test in a separate browser session.

The reader should view the saved CASE-M01 data view and read case records.

  1. If the data view is missing, create it as the administrator in that same space; do not grant management access to fix a saved-object visibility issue.
  2. Run these REST checks in the guest using the password prompt:
ELASTIC01 • Bash
curl --cacert ~/http_ca.crt -u case_reader https://localhost:9200/lab-case-m01/_count
curl --cacert ~/http_ca.crt -u case_reader -H "Content-Type: application/json" -X PUT https://localhost:9200/lab-case-m01/_doc/reader-must-not-write -d '{"message":"permission test"}'

Check: Expect count success and HTTP 403 on the write.

  1. If the write succeeds, the role is too broad: stop, inspect all assigned roles, fix them, remove only that exact test document as administrator, and repeat.
  2. Save evidence.

This checks index write denial; it is not a complete authorization audit. Splunk Free cannot provide this equivalent multi-user control.

3. Run a controlled fault review

Mentor selects one: hide events with the wrong time window; choose a wrong index/data view; add the bad-date fixture to the transformation input; or stop Kibana while leaving Elasticsearch running. Learner must state a hypothesis, inspect the relevant layer, restore the known configuration, and repeat a positive and negative test.

Do not delete volumes, corrupt evidence, or modify the host firewall for this assessment.

Timebox diagnosis to 30 minutes, then explain the remaining uncertainty.

4. Separate lab sizing from operational sizing

Record observed guest RAM, disk growth, startup time, and indexed bytes for each appliance.

These tiny samples cannot establish events-per-second capacity.

  1. Write a capacity plan identifying the measurements a real deployment needs: daily ingestion, bursts, retention, searchable versus archived storage, replicas, recovery objectives, and simultaneous analysts.
  2. Explain why running three different SIEMs would multiply maintenance and parsing work.

Record product edition, version, license limits, and source URL with date.

Wazuh is the core security stack; Elastic teaches indexing/pipeline/detection engineering; Splunk teaches SPL and commercial-product limits; Security Onion teaches network evidence.

Do not label every component open source or assume free tiers include premium SIEM functions.

5. Present a decision and a 30-day handover

Write a two-page recommendation for a fictional 20-person company: its assets and likely threats; selected primary stack; evidence sources; three testable detections; access roles; retention and recovery; update owner; resource budget; and gaps.

Include a one-page appendix with the comparison table and exact query/configuration filenames. Defend why you would select one primary platform, and when a network tool would complement it.

Mentor asks: What evidence would change your conclusion? How would you know the collector stopped? What fails during disk exhaustion? Who can read sensitive logs? How would you restore after a failed upgrade? Score explanations and verified evidence, not screenshots alone.

6. Close the track and rejoin the cloud path

  1. Disable the replay rule, close tunnels, stop containers, and power off the appliance.
  2. Keep original fixtures, configuration exports, query text, hashes, and sanitized reports.
  3. Do not put passwords, tokens, or private data in a portfolio.
  4. Before deleting any VM, verify an exported report and a documented rebuild path with the mentor; checkpoints are not independent backups.

Continue the core cloud sequence in Weeks 23–25 and attach this comparison to the Week 26 final presentation.

Pass this module

  • Reconciled coverage/limitations matrix with actual license and resource observations
  • Reader query succeeds and unauthorized write returns 403
  • Mentor-reviewed recommendation, fault diagnosis, and handover plan

Explain without the guide

  • Which findings are supported across sources, and which remain unknown?
  • What evidence would make you change your preferred platform?

If something fails

Counts differ: return to canonical case label and original index, check duplicates and time range, and separate replay documents. Missing feature: distinguish license limitation from setup failure. A documented limitation is a useful engineering result; an untested claim is not.
