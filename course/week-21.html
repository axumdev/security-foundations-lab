Week 21 / Assurance

Use small scripts to make investigations repeatable

6 hours core+ 0–6 hours practicePrerequisite: Week 20

Security work benefits from small, readable automation even when you do not want to be a software developer. A useful script handles bad input, states its assumptions, and produces a result someone else can verify. This week summarizes logs without changing any system.

Power-on plan: UBU01 only. Work on a copy of Suricata EVE data; no live scanning.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

Expanded track: See the six security-platform labs and schedule for Elastic, Splunk, and Security Onion. Budget these hours separately from the core; complete their comparison report for the final review.

1. Prepare a private working copy

mkdir -p ~/lab/week21
sudo cp /var/log/suricata/eve.json ~/lab/week21/eve-copy.json
sudo chown learner:learner ~/lab/week21/eve-copy.json
chmod 600 ~/lab/week21/eve-copy.json
sha256sum ~/lab/week21/eve-copy.json

If the source is absent, repeat Week 15’s harmless ping test first. Never run a parsing experiment on the only copy of evidence.

2. Create the summarizer

Use nano ~/lab/week21/summarize.py. Enter this complete script:

UBU01 • summarize.py
import json
import sys
from collections import Counter

counts = Counter()
bad = 0
with open(sys.argv[1], encoding="utf-8") as source:
    for line in source:
        try:
            event = json.loads(line)
            if not isinstance(event, dict):
                bad += 1
                continue
            alert = event.get("alert")
            if event.get("event_type") == "alert" and isinstance(alert, dict):
                signature = str(alert.get("signature", "unknown"))
                counts[signature] += 1
        except json.JSONDecodeError:
            bad += 1
for signature, count in sorted(counts.items()):
    print(f"{count}\t{signature}")
print(f"Malformed or non-object lines: {bad}", file=sys.stderr)

3. Run and cross-check

Ubuntu guest • Bash
python3 ~/lab/week21/summarize.py ~/lab/week21/eve-copy.json
jq -r 'select(.event_type=="alert") | .alert.signature' ~/lab/week21/eve-copy.json | sort | uniq -c

Compare counts from two independent methods. Read the script aloud: file input, JSON parsing, filtering, counting, output. A count of zero is possible and meaningful; it is not necessarily a program failure.

4. Test malformed input safely

Ubuntu guest • Bash
cp ~/lab/week21/eve-copy.json ~/lab/week21/test-bad.json
printf "not-json\n" >> ~/lab/week21/test-bad.json
python3 ~/lab/week21/summarize.py ~/lab/week21/test-bad.json

Alert counts should match the original and malformed count should increase by one. A real evidence pipeline should preserve malformed records for investigation; this teaching script only counts them.

5. Track a small change

Ubuntu guest • Bash
cd ~/lab/week21
git init
git config user.name "CyberLab Learner"
git config user.email "learner@example.test"
printf "*.json\n" > .gitignore
git add summarize.py .gitignore
git commit -m "Add local alert summarizer"
git status

Use this local repository only. Commit the script and ignore raw JSON so event data is not accidentally included. A .gitignore entry does not remove files already committed; inspect git ls-files before any future public upload.

Pass this week

  • Script with explained assumptions
  • Independent count comparison
  • Malformed-input test and clean Git file list

Explain without the guide

  • What does the script silently leave out?
  • Why is excluding raw evidence from source control useful?

If something fails

File not found: use the exact path and check pwd/ls. JSON parse errors in jq after adding bad input are expected; use the clean source for the cross-check. Do not “fix” the original evidence by editing it.
