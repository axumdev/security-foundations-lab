Week 14 / Detection

Write and test your first detection rules

6 hours core+ 0–6 hours practicePrerequisite: Week 13

A detection is a testable claim about evidence. It needs a data source, match logic, known positive and negative cases, and a response. Severity is a prioritization signal. A synthetic marker demonstrates plumbing; it is not a production threat detector.

Power-on plan: WAZUH01 + UBU01, 10 GB total. Use WAZUH01 console for edits, dashboard tunnel for later review.

For dashboard access and file transfers, use the complete temporary management procedure in the lab handbook, including the explicit host key path and cleanup checks.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

Expanded track: See the six security-platform labs and schedule for Elastic, Splunk, and Security Onion. Budget these hours separately from the core; complete their comparison report for the final review.

1. Configure a replay log source

On WAZUH01 create the destination before enabling collection:

WAZUH01 • Bash
sudo mkdir -p /var/log/cyberlab
sudo touch /var/log/cyberlab/replay.json
sudo chmod 640 /var/log/cyberlab/replay.json
sudo cp /var/ossec/etc/ossec.conf /var/ossec/etc/ossec.conf.w14-backup
sudo nano /var/ossec/etc/ossec.conf

Inside the existing ossec_config element add:

WAZUH01 • ossec.conf addition
<localfile>
  <log_format>json</log_format>
  <location>/var/log/cyberlab/replay.json</location>
</localfile>

2. Define two small rules

Create /var/ossec/etc/rules/cyberlab_rules.xml with sudo nano.

IDs 100100 and 100101 must be unique in your custom directory; check with sudo grep -R 10010 /var/ossec/etc/rules before saving.

WAZUH01 • cyberlab_rules.xml
<group name="cyberlab,">
  <rule id="100100" level="5">
    <decoded_as>json</decoded_as>
    <field name="lab_source">^cyberlab$</field>
    <field name="action">^test_alert$</field>
    <description>CyberLab synthetic pipeline test</description>
  </rule>
  <rule id="100101" level="5">
    <decoded_as>json</decoded_as>
    <field name="lab_source">^windows_replay$</field>
    <field name="command_line" type="pcre2">CYBERLAB-W13</field>
    <description>CyberLab replayed Windows marker</description>
  </rule>
</group>

3. Test before restarting

WAZUH01 • Bash
sudo /var/ossec/bin/wazuh-logtest

Paste each of these lines separately into logtest.

The first should match 100100; the second should not match your custom marker rule.

Inspect decoder fields and rule ID, not just any generic match.

Input to wazuh-logtest
{"lab_source":"cyberlab","action":"test_alert","case":"W14-A"}
{"lab_source":"cyberlab","action":"normal","case":"W14-B"}

Paste the real CYBERLAB-W13 line from windows-events.json and verify 100101.

Exit with Ctrl+C.

  1. Save a short test table.
  2. If a rule fails parsing, correct it before service restart.

4. Exercise the live collection path

WAZUH01 • Bash
sudo systemctl restart wazuh-manager
sudo systemctl is-active wazuh-manager
printf '%s\n' '{"lab_source":"cyberlab","action":"test_alert","case":"W14-A"}' | sudo tee -a /var/log/cyberlab/replay.json
cat ~/windows-events.json | sudo tee -a /var/log/cyberlab/replay.json > /dev/null
sudo tail -40 /var/ossec/logs/alerts/alerts.json

Append after the collector starts.

In the dashboard filter rule.id:100100 or rule.id:100101 and a recent time range.

Replay ingestion time is now, while event_time in the Windows data is the original event time. This distinction belongs in the report.

5. Tune and describe limitations

Append the normal test event and verify it does not trigger 100100. Try a similar marker with different case; document whether it matches.

  1. Write a rule card: purpose, source/schema, exact match, test data, expected false positives, possible evasions, response, and owner.
  2. Never automatically block a user solely because this training marker appeared.

Pass this week

  • Positive and negative rule tests
  • Manager alert and dashboard trace
  • Rule card with replay-time caveat

Explain without the guide

  • Why can logtest success still fail to produce a dashboard event?
  • What distinguishes this marker test from a useful threat detection?

If something fails

logtest works but no live alert: confirm watched path, append after startup, collector log, manager state, and dashboard filters. Check XML placement and unique IDs. Do not edit bundled rules under /var/ossec/ruleset.

Optional practice · 0–6 extra hours

Add a second benign marker rule with a different ID, then ask your mentor to supply a nonmatching sample that exposes an assumption.
