Week 25 / Cloud

Cloud data access and audit boundaries

6 hours core+ 0–6 hours practicePrerequisite: Week 24

Control-plane Reader lets you see a resource; it does not automatically let you read its blobs. Data access needs a data role. Anonymous access, shared keys, and identity-based access have different control and audit properties. An Activity log is not a substitute for storage data logs.

Power-on plan: Host browser only. One small Azure storage account with dummy data in the dedicated lab resource group. No VM required.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

Expanded track: See the six security-platform labs and schedule for Elastic, Splunk, and Security Onion. Budget these hours separately from the core; complete their comparison report for the final review.

1. Create private-by-default storage

Mentor recreates rg-cyberlab-learner if deleted. Create a Storage account in the agreed region, unique lowercase alphanumeric name, Standard performance, locally redundant storage, general-purpose v2. On Advanced/Security settings require secure transfer, minimum TLS 1.2, disable anonymous blob access, and disable storage account key access for this identity-only exercise. On Networking permit the selected current client public IP only. Portal labels can change; verify the final properties after creation. Do not add private endpoints or paid Defender trials for this core lab.

2. Create and upload dummy data as the instructor

The mentor assigns their own identity Storage Blob Data Contributor at this storage account if needed. Open Data storage → Containers → create evidence with private access. Upload a tiny text file lab-note.txt containing only “CyberLab dummy data.” Use Microsoft Entra user-account authentication in the portal, not account keys. Role propagation can take several minutes.

3. Prove control-plane-only denial

For this test, the learner should have only Reader at the lab resource group and no inherited data role. Mentor temporarily removes the learner’s prior Contributor assignment and assigns Reader. Learner signs out/in to refresh access, opens the storage account, and attempts to read the container through Entra authentication. Expect data-access denial. Confirm the storage firewall permits the current client IP first; a network block would invalidate this role test.

4. Grant the minimum read role

Mentor opens the evidence container → Access control (IAM) → Add role assignment → Storage Blob Data Reader → select learner → Review + assign. Keep resource-group Reader for portal navigation. After propagation, learner refreshes and reads lab-note.txt. Try uploading a second dummy file; it should be denied. Do not “fix” this by granting Owner or enabling shared keys.

5. Test anonymous access and inspect audit coverage

Copy the blob URL and request it in a private browser session without sign-in. It must not reveal the content. Inspect Activity log for role/configuration writes and identify who performed them. Explain that blob reads require separately enabled storage resource logging for a read audit; absence from Activity log is expected. Optional within an approved ingestion budget: on the Blob service Diagnostic settings send StorageRead/Write/Delete logs to a small Log Analytics workspace, repeat the read, and inspect StorageBlobLogs for operation, status, authentication type, and requester fields. Do not enable paid logging without the mentor’s agreed limit.

6. Remove access and clean up

Mentor removes the container data-role assignment; after refresh/propagation learner’s read should fail again. Record that issued tokens/caches can delay a clean test. Export sanitized evidence and delete the whole lab resource group after verifying its contents. Confirm storage and any optional workspace are gone. Review delayed cost records.

Pass this week

  • Reader-only denial, blob-reader success, write denial
  • Anonymous-read denial
  • Audit coverage explanation and cleanup

Explain without the guide

  • Why is a 403 not enough to prove an IAM policy worked?
  • Which log would you need to investigate a blob read?

If something fails

Portal data access fails despite role: check tenant, selected auth mode, inherited roles, role scope, propagation, and client-IP firewall. A changing ISP public IP can invalidate a network test without changing IAM.

Optional practice · 0–6 extra hours

Create a control-plane/data-plane permission matrix and explain how a managed identity would replace a stored application secret.
