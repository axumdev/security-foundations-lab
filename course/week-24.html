Week 24 / Cloud

Deploy and secure a small cloud workload

6 hours core+ 0–6 hours practicePrerequisite: Week 23

A network security group (NSG) controls network traffic at the cloud boundary; a guest firewall controls traffic in the OS. SSH proves access to the machine, not necessarily to the application. This lab exposes SSH only to your current public IP and carries web traffic through a tunnel.

Power-on plan: One mentor-approved Azure Ubuntu 24.04 VM. No local VMs. All resource creation stays in rg-cyberlab-learner.

Your week: Session A (2 h): read, prepare, begin the first steps. Session B (2 h): finish the build and tests. Session C (2 h): troubleshoot, write evidence, and complete mentor review. These are planning estimates; use extra hours for repeats. If a gate fails, carry it forward before dependent labs.

Expanded track: See the six security-platform labs and schedule for Elastic, Splunk, and Security Onion. Budget these hours separately from the core; complete their comparison report for the final review.

1. Create the VM with explicit choices

Azure portal → Virtual machines → Create → Azure virtual machine. Choose the approved subscription/resource group/region. Name az-ubu01. Select Ubuntu Server 24.04 LTS x64 Gen2, a small approved size such as a 1–2 vCPU option if available, SSH public-key authentication, username learner, and generate a new key pair. Choose no public inbound ports initially. Select a standard managed disk and no optional paid monitoring/security trial. Check Review + create for the actual estimated cost before Create. Download the private key securely and keep it out of evidence. Never choose an unreviewed larger size to bypass quota.

2. Restrict the one inbound rule

Open the VM → Networking/Network settings and its NSG. Add an inbound allow rule: source IP Addresses, your current public IPv4 with /32, source port *, destination port 22, protocol TCP, priority 1000, name Allow-SSH-MyIP. Obtain the current public IP from the portal’s “My IP” selector where offered; confirm it belongs to your current connection. Leave the default deny for internet traffic. Do not add 0.0.0.0/0 SSH or web rules. Review effective rules; no broader SSH allow should precede your rule.

3. Connect and patch

Use the VM Connect → Native SSH instructions with the downloaded key and current VM public IP. In host PowerShell:

HOST • PowerShell; replace both tokens
ssh -i "C:\CyberLab\Private\REPLACE_KEY.pem" learner@REPLACE_VM_PUBLIC_IP

Verify the host key through an independent portal Run command reading /etc/ssh/ssh_host_ed25519_key.pub with ssh-keygen -lf before accepting the fingerprint. If Windows OpenSSH rejects key permissions, use a private user-owned directory and restrict that file through Properties → Security; never publish the key.

4. Configure the application and guest boundary

AZ-UBU01 • Bash; replace source IP before executing
sudo apt update
sudo apt upgrade
sudo apt install nginx ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from REPLACE_YOUR_PUBLIC_IP to any port 22 proto tcp
sudo ufw enable
sudo systemctl enable --now nginx
curl -I http://127.0.0.1

Keep your current SSH session open. Open a second session to prove the allow rule before closing the first. If your public IP changes, update both NSG and guest rule through a verified management path; do not widen to everyone.

5. Test through a tunnel

HOST • second PowerShell window
ssh -i "C:\CyberLab\Private\REPLACE_KEY.pem" -N -L 8085:127.0.0.1:80 learner@REPLACE_VM_PUBLIC_IP

Open http://localhost:8085. It should show nginx over the encrypted SSH tunnel. Direct http://VM_PUBLIC_IP should fail because no public HTTP rule exists. This is not an HTTPS certificate deployment; the tunnel provides transport encryption to the guest. Save both positive and negative results.

6. Stop costs deliberately

Close the tunnel. In the portal stop the VM and wait for Stopped (deallocated), not just an OS shutdown. Set a same-day auto-shutdown time if retaining it briefly, accounting for the displayed timezone. Disks and public IP resources may still incur charges. For this course, export evidence and delete the lab resource group at the end of the session unless the mentor explicitly chooses retention. Type the exact group name and confirm only its listed lab resources are included. Verify the group and resources disappear, then review Cost Analysis later for delayed charges. Recreate the group for Week 25.

Pass this week

  • NSG and guest firewall scope
  • Tunnel success and direct-HTTP denial
  • Deallocation/deletion proof and cost review

Explain without the guide

  • How do NSG and guest firewall interact?
  • Why does stopping a VM not guarantee zero cost?

If something fails

SSH timeout: check public IP, source /32, NSG rule priority, VM power state, and guest rule. Key rejection: verify user/key pair and permissions. Use portal Run command for a locked-out guest only within the mentor-approved lab group.

Optional practice · 0–6 extra hours

Record the equivalent Azure CLI commands from portal documentation and explain them; do not deploy a second VM just to demonstrate another interface.
