ALTERNATIVE SETUP / WEEKS 1–3

Build the lab with VirtualBox.

Use this guide for the steps on your physical computer. Use the linked lessons for the commands you type inside Ubuntu.

In development. These instructions target supported Intel or AMD hosts and Ubuntu Server amd64. They have not been piloted end to end. Apple Silicon and later Hyper-V-specific labs are outside this walkthrough.

Week 1 · Prepare the host

  1. Read the lab handbook. Record your host OS, processor, available RAM and disk space. The course plans for 16 GB RAM and recommends 250 GB free for the full sequence.
  2. Back up your work. Create a CyberLab folder with ISOs, VMs and Evidence subfolders. Write down your scope: only your own lab guests.
  3. Choose the base package for your operating system on the official VirtualBox downloads page. Install it and open VirtualBox Manager. The Extension Pack is not required here. Skip the Hyper-V enablement commands in Week 1.

Check: VirtualBox Manager opens and offers to create a VM. If 64-bit guests are unavailable, stop and check host compatibility and virtualization support before changing firmware or security settings.

Week 2 · Build UBU01

  1. Download and verify the Ubuntu Server 24.04 amd64 ISO as described in Week 2, step 1. On Linux use sha256sum filename.iso; replace the filename with the actual download.
  2. In VirtualBox Manager choose New. Name the machine UBU01, select the ISO and Ubuntu 64-bit, and choose manual installation (skip unattended installation). Allocate 2048 MB RAM and two virtual CPUs. Create a new dynamically allocated VDI virtual disk of 40 GB.
  3. Open Settings → Network. Enable only Adapter 1, choose NAT and check Cable Connected. Start the VM. The VM window is its console; you can sign in there without SSH port forwarding.
  4. Follow Week 2, steps 3–5, inside the guest: install to its new virtual disk, name it ubu01, create learner, install OpenSSH, reboot and install the course packages. If asked to remove the installer, use Devices → Optical Drives to eject the ISO. Verify hostname says ubu01 and systemctl is-active ssh returns active.
  5. Run sudo poweroff inside Ubuntu. In Manager select UBU01 → Snapshots → Take; name it w02-clean-linux. Start it again and confirm login. A snapshot depends on the VM disk; it is not a backup.

Week 3 · Connect two guests privately

  1. Repeat Week 2 with a fresh VM and disk named UBU02, hostname ubu02. Install and update using NAT before disconnecting it. Power off both guests cleanly.
  2. For both VMs open Settings → Network → Adapter 1. Change NAT to Internal Network, name it CyberLab-Private on both, and leave Cable Connected checked. Verify there are no other enabled adapters. Bridged reaches your physical network; Host-only includes the host. Neither is the private guest-only setup.
  3. Boot both guests and use their console windows. Follow Week 3, steps 3–4 to set 10.77.0.11/24 and 10.77.0.12/24 with no gateway or DNS. Run ip -br link first and use the actual interface name everywhere, including the capture command; it may be enp0s3 rather than eth0.
  4. In UBU01 start the packet capture from Week 3, step 5. From UBU02 run curl -I http://10.77.0.11. Stop the capture with Ctrl+C and inspect it as shown in that lesson.

What counts as a pass?

  • Both guests boot. Each has one connected adapter on the same Internal Network.
  • Peer ping works, and UBU02 gets an HTTP response from UBU01.
  • The capture on UBU01 shows TCP traffic for that request.
  • Both guests show only the local network route in ip route, with no default route. A failed internet ping alone is insufficient.

If HTTP fails but ping works, check nginx on UBU01. If ping fails, compare the internal network names, link state and addresses. Keep both guests on Internal Network during the test.

For a later update session, replace Internal Network with NAT while the VM is off and use DHCP inside the guest. After updates, restore the internal network and static address and repeat the isolation checks. See Oracle’s networking guide.

Pilot feedback: Record host OS, VirtualBox version, actual interface names and the four results above in your evidence report. Completing these weeks does not validate the rest of the course on VirtualBox.
